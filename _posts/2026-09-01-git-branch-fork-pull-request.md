이번에 정리한 건 **여럿이 쓰는 Git**이다.
브랜치, Fork, Pull Request 같은 말들이 여기서 나온다.

## Git과 GitHub는 다르다

이름이 비슷해서 같은 걸로 착각하기 쉬운데, 하나는 **도구**고 하나는 **서비스**다.

| | Git | GitHub |
|---|---|---|
| 정체 | 내 컴퓨터에서 도는 버전 관리 **도구** | Git 저장소를 위한 온라인 **호스팅 서비스** |
| 하는 일 | 파일이 바뀐 이력을 기록하고 추적 | 원격 저장소 보관, 여러 사람과 협업 |
| 대표 기능 | 브랜치, 커밋 | Pull Request, Issue |

Git은 GitHub 없이도 쓸 수 있다. 인터넷이 끊겨도 커밋은 된다.
GitHub은 그 기록을 **남들과 공유하기 위한** 곳이다.

## 확인하는 명령어 두 개 — `status`와 `log`

둘 다 "확인"이지만 보는 시점이 다르다. **`status`는 지금, `log`는 과거다.**

| | `git status` | `git log` |
|---|---|---|
| 보여주는 것 | 현재 작업 디렉토리의 상태 | 지금까지의 커밋 이력 |
| 구체적으로 | 수정된 파일, `add` 됐는지 여부, 아직 추적 안 되는 파일 | 커밋 작성자, 시각, 커밋 메시지 |

`status`는 "지금 내 책상이 어떤 상태인가", `log`는 "여태 뭘 보냈었나"에 가깝다.

## 명령어를 "왜" 실행하는가

AI Agent에게 작업을 시키면 git 명령어를 알아서 실행하는데,
각각을 **왜** 치는지 알아야 흐름을 따라갈 수 있다.

- **`git branch`** — 지금 어떤 브랜치에 있는지 확인하거나, 작업할 브랜치를 새로 만들려고
- **`git commit`** — 변경한 내용을 하나의 작업 단위로 로컬 저장소에 기록하려고.
  나중에 되돌리거나 추적할 수 있는 **지점을 남기는 것**이다
- **`git diff`** — 수정 전후를 비교해서 **의도한 변경만 들어갔는지** 커밋 전에 검토하려고

## 브랜치 — 독립된 작업 공간

브랜치는 **메인 코드를 건드리지 않고 따로 갈라져서 작업하는 공간**이다.

```
main     ●────●─────────────────●   ← 완성된 코드
              \                /
feature        ●────●────●────┘     ← 여기서 마음껏 실험
                            merge
```

이게 있으면 좋은 점:

- 메인 코드에 영향을 주지 않고 독립적으로 작업할 수 있다
- 여러 사람이 **동시에 서로 다른 기능**을 병렬로 개발할 수 있다
- 작업이 끝나면 **병합(merge)** 해서 하나로 합친다

실험하다 망해도 `main`은 멀쩡하다는 게 핵심이다.

## Fork와 Clone — 둘 다 복사인데, 복사되는 위치가 다르다

여기가 제일 헷갈렸다. 둘 다 "가져온다"는 느낌이라 그렇다.
**결과물이 어디에 생기는지**로 구분하면 명확해진다.

| | Fork | Clone |
|---|---|---|
| 무엇을 | 다른 사람의 GitHub 저장소를 | GitHub의 저장소(원본이든 Fork본이든)를 |
| 어디로 | **내 GitHub 계정**으로 복사 | **내 컴퓨터**로 내려받기 |
| 수단 | GitHub의 기능 | Git 명령어 |

그래서 팀 작업 순서는 보통 이렇게 된다.

```
Fork  →  Clone  →  로컬 작업
(내 계정)  (내 컴퓨터)
```

## Pull Request — "합쳐 주세요"라고 요청하는 것

공유받은 저장소에서 작업을 마친 뒤,
그 변경 사항을 **원본 프로젝트에 병합해 달라고 요청**하는 것이 Pull Request(PR)다.

그냥 합치면 될 것을 왜 요청하냐면:

- 변경 사항을 저장소 관리자에게 **공식적으로 검토받을 수 있다**
- 팀원들과 코드에 대해 **논의하고 피드백**을 주고받을 수 있다
- 병합되기 전 **마지막으로 확인하는 단계** 역할을 한다

## feature 브랜치를 main에 반영하는 5단계

순서가 중요하다. 이 순서대로 해야 충돌 없이 안전하게 병합된다.

1. **로컬에서 commit** — 변경 내용을 로컬 저장소에 기록
2. **feature 브랜치 push** — 커밋을 GitHub 원격 저장소에 업로드해 공유
3. **Pull Request 생성** — main에 병합해달라고 공식 요청, 리뷰 대상으로 등록
4. **코드 검토** — 다른 사람이 코드 품질·오류 여부 확인
5. **Pull Request merge** — 검토 통과 후 실제로 main에 통합

> **commit → push → PR 생성 → 코드 검토 → merge**
{: .prompt-tip }

## add를 안 하면 commit이 안 되나?

정리하다가 궁금해서 물어봤다. 답은 **그렇다**.

`git commit`은 **스테이징 영역에 있는 것만** 커밋한다.
`git add`로 먼저 올려두지 않으면 커밋할 게 없어서 안 된다.

다만 예외가 하나 있다.

- **이미 한 번 커밋된 적 있는(추적 중인) 파일을 수정한 경우**라면
  `git commit -a`로 add를 건너뛰고 바로 커밋할 수 있다
- 하지만 이 경우에도 **새로 추가된 파일(untracked file)은 자동으로 포함되지 않는다.**
  그 파일들은 여전히 `git add`가 필요하다

즉 `-a`는 "이미 알고 있는 파일들의 수정분"만 챙겨준다.

## 핵심 정리

| 용어 | 한 줄 정의 |
|---|---|
| Branch | 독립적인 작업 공간 |
| Commit | 변경 내용 기록 |
| Diff | 변경 전후 비교 |
| Fork | 내 GitHub 계정으로 복사 |
| Clone | 내 컴퓨터로 다운로드 |
| Pull Request | 병합 요청 및 코드 검토 |

## 아직 안 해본 것

개념은 정리했는데 **브랜치를 직접 만들어본 적은 아직 없다.**
이 블로그 저장소도 확인해보니 `main` 하나뿐이다.

```
* main
  remotes/origin/main
```

혼자 쓰는 저장소라 당장 나눌 일이 없어서인데,
Fork와 Pull Request도 마찬가지로 아직 **읽어서 아는 것**에 머물러 있다.
