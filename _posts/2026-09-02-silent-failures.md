블로그를 손보면서 하루 동안 세 번 막혔다. 공통점이 있었다.
**셋 다 오류 메시지를 안 줬다.** 실패했다고 알려주지 않고, 성공한 얼굴로 결과만 달랐다.

## 1. 미래 시각으로 적으면 글이 사라진다

09시 28분에 글을 쓰면서 발행 시각을 이렇게 적었다.

```yaml
date: 2026-09-01 09:30:00 +0900
```

09:30은 그 시점 기준으로 **2분 뒤, 아직 오지 않은 시각**이다.

push하고 GitHub Actions를 봤더니 **초록색 체크, 빌드 성공.**
그런데 사이트에 들어가니 **그 글만 없었다.**

원인은 Jekyll의 예약 발행 기능이었다.
블로그 도구들은 보통 "내일 오전 9시에 공개" 같은 예약 기능이 있는데,
Jekyll은 그걸 `date` 하나로 판단한다.
**지금보다 미래면 → 아직 공개할 때가 아니네 → 빌드 결과물에서 뺀다.**

무서운 건 여기다.

| 상황 | 알아채기 |
|---|---|
| 빌드가 실패함 | 빨간 X. 바로 안다 |
| 빌드는 성공, 결과물만 빠짐 | **어디서부터 봐야 할지 모른다** |

로그에도 경고 한 줄 없다. 시각을 `08:00` 으로 고쳐 push하니 바로 올라왔다.

> 글 쓰기 전에 현재 시각을 확인하고 **그보다 이른 시각**을 적는다.
> 아예 `08:00:00 +0900` 같은 이른 아침 시각을 박아두는 게 안전하다.
{: .prompt-tip }

## 2. 파일명에 한글을 쓰면 URL이 깨진다

첫 글 파일명이 `2026-08-31-git-기초-add-commit-push.md` 였다.
한글은 `기초` 한 단어뿐인데, URL에서는 이렇게 부풀어 나온다.

```
.../posts/git-%EA%B8%B0%EC%B4%88-add-commit-push/
```

브라우저 주소창은 `기초` 로 예쁘게 보여준다. 그래서 문제인 줄 몰랐다.
**링크를 복사해서 카톡에 붙이면 저 깨진 형태로 나간다.**

그래서 `git-기초` → `git-basics` 로 바꿨다.
**글 제목의 `기초` 는 그대로 뒀다.** 제목은 화면에 보이는 것이고 URL에 안 쓰인다.

### `git mv` - 이름 바꾸기와 add를 한 번에

파일 이름을 바꿀 때 탐색기에서 바꾸면 git은 이걸 *삭제 + 새 파일*로 본다.

```
D  2026-08-31-git-기초-add-commit-push.md
?? 2026-08-31-git-basics-add-commit-push.md
```

`git mv` 를 쓰면 이름 변경과 `git add` 를 한 번에 하고, 한 줄로 잡힌다.

```bash
git mv 옛이름.md 새이름.md
```

```
R  2026-08-31-git-기초-...md -> 2026-08-31-git-basics-...md
```

커밋 결과에도 차이가 남는다.

```
1 file changed, 0 insertions(+), 0 deletions(-)
rename ... (100%)
```

내용이 한 글자도 안 바뀌고 이름만 바뀐 걸 git이 알아서 기록했다는 뜻이다.

## 3. 파일명을 바꿨더니 빌드가 죽었다

여기서 두 번째로 막혔다. 이름을 바꾸고 push했더니 **이번엔 빌드가 실패했다.**

원인은 다른 글에 있던 이 한 줄이었다.

```
[앞 글]({% post_url 2026-08-31-git-기초-add-commit-push %})
```

`{% post_url %}` 은 빌드할 때 **"그 파일명의 글"을 찾아 주소로 바꿔주는 문법**이다.
파일명을 바꿔버렸으니 찾을 수 없는 글을 가리키게 됐고,
Jekyll은 이걸 **경고가 아니라 오류로 처리**해서 `Build site` 단계에서 멈췄다.

→ **파일명을 바꾸기 전에 참조부터 찾아야 한다.**

```bash
grep -rn "post_url" --include="*.md" _posts/
```

다행인 점이 하나 있었다.
빌드가 실패하면 `deploy` 단계가 skip되므로 **사이트는 직전 상태로 살아 있다.**
방문자에게 깨져 보이지는 않는다. 대신 새 변경사항도 반영되지 않는다.

## 빌드 결과는 로그인 없이도 볼 수 있다

공개 저장소라면 Actions 결과를 API로 확인할 수 있다.
브라우저로 Actions 탭에 들어가지 않아도 된다.

```bash
curl -s "https://api.github.com/repos/사용자명/저장소명/actions/runs?per_page=3"
```

`status`, `conclusion`, `head_commit.message` 를 보면 성공/실패를 알 수 있다.
어느 단계에서 죽었는지까지도 볼 수 있다.

```bash
curl -s ".../actions/runs/<RUNID>/jobs" | grep -E '"(name|conclusion)"'
```

**다만 로그 본문은 GitHub 로그인이 필요하다.** 웹으로 열어도 "Sign in to view logs"가 뜬다.
로그를 못 보는 상황에서는 **저장소를 직접 grep해서 원인을 추론**하는 편이 빨랐다.
위의 `post_url` 문제도 그렇게 찾았다.

## 4. 고친 글이 안 보인다 - 서비스 워커 캐시

세 번째. 글을 고쳐서 배포했는데 이상했다.

- 새로고침하면 → **새 내용**
- 주소로 다시 들어가면 → **옛 내용**

원인은 Chirpy의 PWA 서비스 워커였다. 코드를 열어보니 이렇다.

```js
caches.match(요청).then(캐시된것 => 캐시된것 || fetch(요청))
```

**캐시에 있으면 서버에 아예 물어보지 않는다.** 최신인지 확인조차 안 한다.
강제 새로고침(`Ctrl+Shift+R`)은 이 과정을 건너뛰기 때문에 최신이 나왔던 것이다.

일반적인 원칙은 파일 종류에 따라 다르게 다루는 것이다.

- **CSS·JS·이미지** — 내용이 바뀌면 파일명이 바뀌게 만들어 둔다.
  그래서 캐시를 그냥 써도 안전하다
- **HTML(글 페이지)** — 주소는 그대로인데 내용만 바뀐다.
  서버에 먼저 묻거나, 캐시를 보여주면서 동시에 새로 받아와 다음번에 반영하는 방식을 쓴다

Chirpy는 이 구분 없이 HTML까지 cache-first로 처리한다. 일반 권장과 어긋난다.

**이건 아직 결론을 안 냈다.** 어떻게 할지는 더 보고 정하기로 했다.

## 커밋 시각은 감출 수 없다

"지금 발행하면 수업시간에 발행한 기록이 남나?" 싶어서 확인해봤다.

페이지 HTML에 이런 게 들어 있다.

```html
<time data-ts="1788225507" ...> Sep 1, 2026 </time>
```

저 숫자를 시각으로 바꾸면 **커밋한 실제 시각**이 나온다.

| 어디 | 남는 시각 | 내가 정할 수 있나 |
|---|---|---|
| GitHub 커밋 히스토리 | 실제 커밋 시각 | ❌ |
| GitHub Actions 실행 기록 | 실제 push 시각 | ❌ |
| 블로그 페이지 `Updated` | 실제 커밋 시각 | ❌ |
| 블로그 페이지 `Posted` | front matter의 `date` | ⭕ |

즉 화면에 보이는 발행일(`Posted`)은 정할 수 있지만,
**커밋 시각은 공개 저장소에 그대로 남는다.**

## 곁가지 - 커밋 전에 `git diff`

"태그 하나 바꾼 걸 어떻게 확인하고 푸시하냐"는 궁금증에서 배운 것.

```bash
git diff
```

- `-` 로 시작하는 줄 = 빠진 줄
- `+` 로 시작하는 줄 = 들어간 줄
- `@@ -3,7 +3,7 @@` = 3번째 줄 근처

**한 단어만 바꿔도 "줄 전체가 빠지고 다시 들어옴"으로 표시된다.**
git이 줄 단위로 비교하기 때문이다.

## 오늘 반복해서 나온 말

**"확인해보기 전에는 모른다."**

- 미래 시각으로 적으면 글이 사라진다 → 빌드는 성공이라 원인을 못 찾는다
- 파일명을 바꾸면 다른 글의 참조가 끊긴다 → 미리 grep해야 안다
- 고친 글이 안 보인다 → 서비스 워커 코드를 열어봐야 안다

**조용히 실패하는 것이 시끄럽게 실패하는 것보다 위험하다.**
빨간 X는 최소한 어디를 봐야 할지 알려준다.
