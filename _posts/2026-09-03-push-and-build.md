글 한 편을 올리는 동안 사고가 두 번 났다.
하나는 **올리지 않기로 한 커밋이 같이 올라간 것**, 다른 하나는 **글 때문에 빌드가 죽은 것**이다.
둘 다 "올린다"와 "사이트에 뜬다"가 다른 일이라는 걸 몰라서 생긴 문제였다.

## 1. `git push` 는 커밋을 하나만 보내지 않는다

글 한 편을 커밋하고 push했는데, 로컬에만 두기로 했던 커밋이 **같이 올라갔다.**

`git push` 는 그 브랜치에 쌓인 커밋을 **전부** 보낸다.
방금 만든 커밋 하나만 골라 보내는 게 아니다.

커밋을 만들 때는 한 개씩 만드니까 push도 한 개씩 갈 것 같은데, 그렇지 않다.
push는 **"내 브랜치를 원격 브랜치와 같게 만들어라"** 는 명령에 가깝다.

그래서 push 전에 무엇이 올라갈지 보는 명령이 필요하다.

```bash
git log origin/main..HEAD
```

`origin/main..HEAD` 는 **원격에는 없고 내 쪽에만 있는 커밋**을 뜻한다.
비어 있으면 올라갈 게 없다는 뜻이고, 목록이 나오면 그게 전부 간다.

`--oneline` 을 붙이면 한 줄씩 짧게 볼 수 있다.

```bash
git log origin/main..HEAD --oneline
```

같은 명령을 push **뒤**에 쓰면 확인용이 된다.
비어 있으면 남김없이 올라갔다는 뜻이다.

## 2. 코드 블록 안의 `{% raw %}{% %}{% endraw %}` 도 Jekyll이 실행한다

"파일명을 바꿨더니 링크 참조가 끊겨 빌드가 죽었다"는 내용을 글로 쓰면서,
문제가 됐던 그 코드를 **예시로 코드 블록에 그대로 적었다.**

그랬더니 **똑같이 빌드가 죽었다.**

Jekyll은 코드 블록 안이라도 `{% raw %}{% %}{% endraw %}` 를 명령으로 읽는다.
화면에는 회색 상자 안 글자로 보이지만, Jekyll에게는 그냥 실행할 코드다.
그래서 이미 없어진 파일을 또 찾으러 갔고, 어제와 똑같은 자리에서 멈췄다.

해결은 `raw` 태그로 감싸는 것이다.
여는 태그는 `{% raw %}{% raw %}{% endraw %}` 이고, 닫는 태그는 같은 모양에 `end` 를 붙인 것이다.
감싼 안쪽은 명령이 아니라 글자로 취급된다.

`{% raw %}{{ }}{% endraw %}` 로 쓰는 변수는 오류까지 나지는 않지만
값이 치환돼 버리니 역시 감싸는 편이 낫다.

> **삽질을 글로 쓸 때, 그 삽질을 글 안에서 그대로 재현할 수 있다.**
> 이 글에서도 위의 예시들은 전부 `raw` 로 감싸서 썼다.
{: .prompt-tip }

## 3. push했는데 사이트에 안 보이는 이유

두 사고를 겪고 나서야 단계가 나뉘어 있다는 게 눈에 들어왔다.

| 단계 | 하는 일 | 걸리는 시간 |
|---|---|---|
| `git push` | 파일을 GitHub 창고에 올림 | 몇 초 |
| **빌드** | 그 파일들로 웹사이트를 만듦 | 1~2분 |
| 배포 | 만들어진 사이트를 주소에 올림 | 몇 초 |

올리는 건 `.md` 파일이다. 브라우저는 이걸 못 읽는다.
빌드 단계에서 Jekyll이 HTML로 바꾸고, 테마 옷을 입히고,
글 목록·태그 페이지·검색 색인을 새로 만든다.

그래서 **빌드가 실패하면 파일은 GitHub에 멀쩡히 있는데 사이트에는 안 나온다.**
저장소에서 파일을 확인하고 "올라갔네"라고 판단하면 틀린다.

빌드 결과는 로그인 없이도 확인할 수 있다.

```bash
curl -s "https://api.github.com/repos/ctaleez51-art/blog_kate/actions/runs?per_page=3"
```

## 정리

- `git push` 는 브랜치의 커밋을 전부 보낸다. 하나만 골라 보내지 않는다
- push 전에 `git log origin/main..HEAD` 로 무엇이 갈지 본다. push 뒤엔 확인용이 된다
- Jekyll은 코드 블록 안의 태그도 실행한다. 예시로 쓸 땐 `raw` 로 감싼다
- push는 창고에 넣는 것까지다. 사이트가 되는 건 빌드와 배포가 끝난 뒤다
