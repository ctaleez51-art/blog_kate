저장소를 네 개 만들어놓고도 정작 **저장소 화면에 있는 메뉴들이 뭔지**는 몰랐다.
파일 목록만 보고 나왔다. 하나씩 확인했다.

## 먼저, sign in 과 sign up

- **sign up** — 계정을 새로 만드는 것. 처음 한 번만 한다
- **sign in** — 이미 만든 계정으로 들어가는 것

log in = sign in, register = sign up. 같은 뜻의 다른 표현이다.

## 위쪽 탭

| 메뉴 | 역할 |
|---|---|
| Code | 파일 목록. 기본 화면 |
| Issues | 할 일·버그를 글로 등록해두는 곳 |
| Pull requests | 브랜치 변경사항을 합쳐달라고 요청하는 곳 |
| Agents | GitHub의 AI에게 작업을 시키는 곳 |
| Actions | push 같은 일이 생기면 자동 실행되는 작업. **여기서 블로그가 빌드된다** |
| Projects | 이슈를 칸반보드처럼 늘어놓고 관리하는 곳 |
| Wiki | 저장소에 딸린 문서 공간 |
| Security and quality | 취약점·보안 설정 |
| Insights | 커밋 통계, 기여자 등 활동 그래프 |
| Settings | 저장소 이름, 공개/비공개, Pages 등 설정 |

## 오른쪽 위 버튼

| 버튼 | 역할 |
|---|---|
| Pin | 내 프로필 첫 화면에 이 저장소를 고정 |
| Watch | 이 저장소의 알림 받기 |
| Fork | 남의 저장소를 내 계정으로 복사 |
| Star | 즐겨찾기 |

## 사이드바

| 항목 | 역할 |
|---|---|
| About | 저장소 설명·주소 |
| Activity | 저장소에 있었던 일 기록 |
| Releases | 배포판을 묶어 내려받게 하는 기능 |
| Deployments | 배포 상태. 초록 체크면 성공 |
| Packages | 라이브러리 배포 기능 |
| Contributors | 커밋한 사람 |
| Languages | 파일 확장자로 계산한 언어 비율 |

## 남이 내 저장소를 고칠 수 있나

`Public` 저장소라 신경 쓰였던 부분이다.

- **보는 건 된다.** 파일도 커밋 기록도 누구나 전부 볼 수 있다
- **수정은 안 된다.** 쓰기 권한이 있는 사람만 push할 수 있다

남이 할 수 있는 최대는 **Fork로 자기 계정에 복사해서 고친 뒤 Pull Request로 제안**하는 것까지다.
받아들일지는 저장소 주인이 정한다.

권한을 따로 주려면 `Settings` → `Collaborators` 에서 상대방 계정을 초대하면 된다.
상대가 수락하면 그때부터 직접 push할 수 있다.

## 내 블로그는 어떻게 들어가나

저장소를 눌러도 나오는 건 파일 목록이다. **블로그 화면은 주소가 따로 있다.**

그래서 일반적인 방법은 **사이트 주소를 북마크해두고 그걸로 들어가는 것**이다.
GitHub는 코드 저장소지 블로그 관리 화면이 아니라서, 네이버 블로그처럼 "내 블로그 가기" 버튼이 없다.
만든 사람도 주소로 들어간다.

저장소에서 굳이 찾아 들어가려면 사이드바 `Deployments` → `github-pages` 를 누르면 주소가 있다.

## deployment 가 무슨 뜻인가

만들어진 결과물을 **실제로 서비스되는 자리에 갖다 놓는 것**이다. 우리말로 배포다.

화면의 `Deployments` 는 그 일이 일어난 **기록**이다.
블로그라면 빌드로 만들어진 웹사이트가 `github.io` 주소에 올라간 건들이다.

## 정정 - `Deployments` 옆의 숫자

이 숫자에 대해 **전에 잘못 정리한 적이 있다.** "환경(environment) 개수라서 항상 1"이라고 썼다.
확인해보니 틀렸다.

| 저장소 | environments | deployments | 화면 숫자 |
|---|---|---|---|
| blog_kate | 1 | **18** | **18** |
| pixel_runner | 1 | 2 | (당시 1로 보였음) |

환경은 두 저장소 다 1개인데 화면 숫자는 18과 1로 달랐다. 그러니 그 숫자는 **배포 횟수**다.

당시 pixel_runner에서 1로 보였던 건 그 시점에 배포가 한 건만 끝나 있었을 가능성이 크다.
**"2건인데 1로 나온다"는 것 하나만 보고 단정한 것**이 잘못이었다.

## 곁가지 - 블로그에 Liquid 태그를 예시로 쓸 때

Jekyll에서 `raw` 태그를 **설명하는 글**을 쓰다 알게 된 것이다.

여는 태그는 `raw` 로 감싸면 글자로 표시된다. 그런데 **닫는 태그는 그게 안 된다.**
감싸도 그 안에서 먼저 닫혀버려서 뒤에 태그 하나가 남고,
Jekyll이 짝 없는 태그로 읽어서 빌드가 죽을 수 있다.

결국 **"닫는 태그는 같은 모양에 `end` 를 붙인 것"** 이라고 문장으로 풀어 썼다.

## 정리

- 저장소 화면에서 실제로 자주 쓸 건 `Code`, `Actions`, `Settings`, `Deployments` 정도다
- 공개 저장소는 누구나 볼 수 있지만 고칠 수는 없다. 권한은 `Collaborators` 로 준다
- 블로그는 주소를 북마크해서 들어간다. GitHub에 그런 버튼은 없다
- `Deployments` 옆 숫자는 **배포 횟수**다
