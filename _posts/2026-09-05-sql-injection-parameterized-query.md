> Claude와의 대화 내용을 Claude가 초안으로 정리하고, 제가 검토·수정했습니다.
{: .prompt-info }

수업에서 "Little Bobby Tables" 이야기가 나왔다.
아들 이름을 이렇게 지은 엄마 이야기다.

```
Robert'); DROP TABLE Students;--
```

학교에 등록하니 학생 표가 통째로 지워졌다는 농담이다.

**그냥 글자인데 왜 명령이 되나.** 이게 오늘 가장 오래 붙든 질문이다.

## 데이터베이스가 받는 것은 한 덩어리의 문장이다

프로그램이 이름으로 학생을 찾을 때, 대충 이런 문장을 만들어 보낸다.

```sql
SELECT * FROM Students WHERE name = '입력받은이름'
```

여기서 중요한 건 **문장을 누가 완성하느냐**다.

프로그램이 이름을 저 자리에 끼워 넣어 **완성한 다음** 통째로 보낸다.
그 순간 **어디까지가 프로그래머가 쓴 것이고 어디부터가 사용자가 넣은 값인지 표시가 사라진다.**

데이터베이스가 받는 것은 구조가 아니라 그냥 글자 한 줄이다.
앞에서부터 읽으면서 따옴표를 만나면 "여기가 값의 시작"이라고 보고,
다음 따옴표를 만나면 "여기가 값의 끝"이라고 본다.

**그런데 이름 안에 따옴표가 들어 있으면?**

## 그 이름이 실제로 하는 일

`Robert'); DROP TABLE Students;--` 를 하나씩 뜯어보면 이렇다.

| 조각 | 하는 일 |
|---|---|
| `'` | 값을 **닫는다.** 여기까지가 이름이라고 선언 |
| `)` | 열려 있던 괄호를 닫는다 |
| `;` | 문장을 **끝낸다** |
| `DROP TABLE Students` | **새 명령을 얹는다.** 학생 표를 지워라 |
| `--` | 뒤에 남은 조각을 **주석 처리**한다 |

마지막 `--` 가 중요하다.
프로그래머가 쓴 문장의 뒷부분(닫는 따옴표 같은 것)이 남아 있으면 문법이 깨지는데,
주석으로 만들어서 없는 셈 친다.

그래서 **문법에 흠이 하나도 없는 문장**이 된다.
데이터베이스는 거절할 이유가 없다. 시킨 대로 할 뿐이다.

## 데이터베이스가 규칙을 어긴 게 아니다

이 부분이 인상적이었다.

데이터베이스는 버그를 낸 게 아니다. 속은 것도 아니다.
**문법에 맞는 명령을 받아서 그대로 실행했을 뿐이다.**

> 원인은 **명령과 데이터를 하나로 섞어서 건넨 쪽**에 있다.
{: .prompt-warning }

## 막는 법 - 파라미터화 쿼리

수업 자료에는 이렇게 적혀 있었다.

> 자리표(`?`)를 비워 두고 입력은 따로 건넨다

읽고도 무슨 말인지 몰라서 다시 물었다.
자리를 비우든 안 비우든 결국 값이 들어가는 건 똑같은데 뭐가 다르냐는 게 걸렸다.

다시 잡은 설명은 **"문장이 언제 완성되는가"** 였다. 이걸로 통했다.

### 위험한 방식 - 완성해서 보낸다

```
프로그램: 이름을 끼워 넣어 문장을 완성한다
        → 데이터베이스에 보낸다
데이터베이스: 받은 한 덩어리를 해석한다
```

데이터베이스가 처음 볼 때 **이미 섞여 있다.** 구분할 방법이 없다.

### 안전한 방식 - 뼈대를 먼저 보낸다

```
프로그램: 자리를 비운 뼈대를 먼저 보낸다
        SELECT * FROM Students WHERE name = ?
데이터베이스: 이 문장을 먼저 해석해서 구조를 확정한다
        - 조회 명령이다
        - 명령은 하나다
        - 값이 하나 들어올 자리가 있다
프로그램: 그 다음에 값을 따로 건넨다
데이터베이스: 확정된 자리에 값으로만 넣는다
```

**구조가 이미 못 박힌 뒤에 값이 도착한다.**

그래서 값 안에 따옴표가 있든 세미콜론이 있든 상관이 없다.
해석은 이미 끝났다. 그것들은 명령이 아니라 **그냥 글자**다.

`Robert'); DROP TABLE Students;--` 를 넣으면 어떻게 되나?
**그런 이름의 학생을 찾아보고, 없다고 답한다.** 그게 전부다.

## 걸러내는 것과는 다르다

처음엔 "위험한 글자를 검사해서 막는 것"인 줄 알았다.
따옴표가 들어오면 거르고, `DROP` 이 보이면 막고.

그게 아니었다.

| | 방식 |
|---|---|
| 거르기 | 위험한 글자를 찾아서 막는다. **뚫릴 방법을 계속 찾아야 한다** |
| 파라미터화 | 애초에 **명령으로 읽힐 수 없는 자리**에 넣는다 |

거르기는 공격자와 술래잡기를 하는 것이다. 새로운 우회 방법이 나오면 또 막아야 한다.
파라미터화는 술래잡기 자체를 안 한다. 값이 명령이 될 수 있는 통로를 없앤 것이다.

## 정리

- 데이터베이스는 **한 덩어리의 문장**을 받는다. 그 안에서 명령과 값을 구분할 표시가 없다
- 값 안에 따옴표를 넣으면 값을 닫고 **새 명령을 이어붙일 수 있다**
- 데이터베이스가 잘못한 게 아니다. **섞어서 건넨 쪽**의 문제다
- 파라미터화 쿼리는 **뼈대를 먼저 보내 구조를 확정한 뒤** 값을 따로 건넨다
- 핵심은 거르는 것이 아니라 **명령으로 읽힐 수 없는 자리에 넣는 것**
