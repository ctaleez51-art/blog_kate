오늘 과제는 자주 반복하는 작업을 스킬 파일로 만들어 GitHub에 올리고 주소를 제출하는 것이었다.
주제는 **블로그 자동 발행**으로 정했다. 매일 아침 실제로 반복하는 작업이고,
규칙이 이미 `CLAUDE.md`에 적혀 있어서 새로 짜낼 게 없었다.

## 스킬은 몸이 들고 있는 설명서

앞 글에서 머리(LLM)와 몸(하네스) 얘기를 했다. **스킬은 몸이 들고 있는 설명서**다.

"엑셀 다룰 때는 이렇게 해라"라고 적어둔 설명서가 있으면,
엑셀 일이 들어올 때 몸이 그 설명서를 꺼내서 머리에게 보여준다. 머리는 그걸 읽고 적힌 대로 한다.

그래서 매번 처음부터 알아서 하는 게 아니라, **정해둔 방식대로 하게** 만드는 물건이다.

## CLAUDE.md와 무엇이 다른가

하는 일은 똑같다. 적어두면 읽고 그대로 하는 설명서다.
차이는 **언제 읽히느냐** 하나였다.

- `CLAUDE.md` — 대화를 새로 열 때마다 **무조건** 읽힌다. 블로그 얘기를 안 해도 읽힌다
- **스킬** — 블로그 쓸 일이 생겼을 때만 그 설명서를 펴는 것

GPTs나 Gems에 미리 지침을 입력해 두는 것도 같은 것인지 물었다. 같았다.
미리 지침을 적어두고 꺼내 쓴다는 점에서 하는 일이 똑같다.

남는 차이는 **누가 고르느냐** 하나다.
GPTs는 제목용을 열지 대본용을 열지 사용자가 직접 고른다.
스킬은 일감을 보고 어느 설명서를 꺼낼지 LLM이 고른다.

## 누가 언제 만드나

만드는 쪽은 세 곳이다. 만든 회사가 미리 넣어둔 것, 사용자가 직접 쓴 것,
남이 만들어 공개한 걸 갖다 쓴 것.

만드는 때는 **같은 일을 또 하게 될 때**다.
한 번만 할 일이면 그냥 말로 시키면 되고, 매번 똑같은 걸 설명하는 게 귀찮아지면 그때 적어둔다.

내가 이미 하나 만들어 둔 셈이었다. 블로그 규칙이 그거였다.
매번 "안내 박스 넣고 파일명은 영문으로"를 설명하는 대신 파일에 적어둔 거니까.

## SKILL.md 생김새

스킬 폴더 안 `SKILL.md`는 두 부분이다. 맨 위 **머리말**(이름·설명)과 그 아래 **본문**(실제 지시).

```markdown
---
name: blog-publish
description: daily/ 폴더의 전날 학습 기록을 읽어 블로그 글 초안을 만들고, 승인 후 발행한다.
---

# 블로그 자동 발행

## 언제 쓰나
...
```

`description` 한 줄이 중요하다. **언제 이 스킬을 꺼낼지를 그 한 줄로 판단하기 때문이다.**

## 슬러그 — 원래 무슨 뜻인가

초안에 `blog_kate/_posts/YYYY-MM-DD-슬러그.md` 라고 적혀 있었는데, 슬러그가 뭔지 몰라서 물었다.

주소에 들어갈 제목이다. 영어 소문자로, 띄어쓰기 대신 하이픈을 쓴다.
`2026-08-31-git-basics-add-commit-push.md` 에서 `git-basics-add-commit-push` 가 슬러그고, 그대로 주소가 된다.

원래 뜻은 **민달팽이**, 그리고 **금속 덩어리**였다.
옛날에 신문을 납활자로 짤 때 한 줄을 통째로 부어 만든 금속 조각을 slug이라고 불렀고,
거기서 신문사 말로 "기사에 붙이는 짧은 이름표"라는 뜻이 생겼다.
제목이 아직 안 정해졌어도 편집실에서 부를 이름은 있어야 하니까. 웹에서 그 말을 그대로 가져다 쓴 것이다.

## 초안을 보다가 빠진 걸 찾았다

초안에 「여러 편일 때」 항목은 있는데 **언제 여러 편이 되는지가 없었다.**
지금까지 발행된 글을 보면 주제 하나당 한 편으로 나뉘어 있어서, 그 기준을 넣기로 했다.

```markdown
## 여러 편으로 나누기

**주제 하나당 한 편**이다. daily/ 파일에서 다룬 주제를 세어, 그 수만큼 글을 만든다.
```

## 제출 절차

```bash
git status --short          # ?? SKILL.md  (새 파일, 아직 추적 안 됨)
git add SKILL.md
git commit -F -             # 여러 줄 메시지
git log origin/main..HEAD --oneline
git push
```

`LF will be replaced by CRLF` 경고는 줄바꿈 방식 차이라서 문제 없다.
제출 주소는 `https://github.com/ctaleez51-art/PROJECT/blob/main/SKILL.md` 가 됐다.

## GitHub에 올린 것과 작동하는 것은 다르다

여기서 한참 헷갈렸다. GitHub에 올렸으니 스킬로 쓰이는 거 아닌가 싶었는데 아니었다.

**클로드는 GitHub에 있는 파일을 읽지 않는다.** 내 컴퓨터의 정해진 폴더에 있는 것만 읽는다.

```
C:\Users\ctale\.claude\skills\blog-publish\SKILL.md
```

`PROJECT` 저장소에 있는 건 **제출용 사본**이었다.
실제로 작동시키려면 위 자리에 복사해 넣어야 했다. 폴더는 명령어로 만들든 탐색기로 만들든 같다.
그리고 이 폴더는 **GitHub 연동이 필요 없다.** 내 컴퓨터에만 있는 자리다.

넣고 나서도 그 창에서는 안 잡혔다.
스킬 목록은 대화를 시작할 때 한 번 읽어서, **새 창을 열어야** 보인다.

## 여러 개 만들려면 — 파일명은 다 같고 폴더로 구분한다

반복 작업이 새로 생길 때마다 폴더를 하나씩 더 만든다.
**파일 이름은 항상 `SKILL.md` 로 같고, 폴더 이름으로 구분한다.**

```
C:\Users\ctale\.claude\skills\
├── blog-publish\SKILL.md
├── rss-summary\SKILL.md
└── content-repurpose\SKILL.md
```

폴더 이름은 영문 소문자·하이픈으로 짓고, 머리말의 `name` 도 같게 쓴다.

## CLAUDE.md를 줄이는 이유

같은 내용이 두 곳에 있으면 `CLAUDE.md` 쪽을 빼는 게 맞다.

- `CLAUDE.md` 는 **매번 무조건 읽힌다.** 길어지면 매 대화에서 그만큼을 계속 읽는다
- 스킬은 **필요할 때만 읽힌다.** 블로그를 안 쓰는 날엔 읽지 않는다

블로그 절차처럼 "특정 작업을 할 때만 필요한 것"은 스킬이 맞는 자리다.
`CLAUDE.md` 에는 항상 알아야 하는 것만 남긴다.

단, **스킬이 실제로 작동하는지 확인한 뒤에** 빼야 한다.
안 잡히는 상태에서 빼면 규칙이 그냥 사라진다.

## 파일 쓰다 걸린 것 — heredoc 안에 heredoc

기록 파일을 셸의 heredoc으로 쓰려고 했는데, 본문에 예시로 적은 종료 표시 때문에
명령이 중간에 끊겼다. 셸이 본문 속 그 줄을 진짜 종료로 읽은 것이다.

셸 문법 예시가 들어갈 내용은 셸을 거치지 않는 파일 쓰기 방식을 쓰는 게 맞다.
