> 모두의연구소 AI 에이전트 과정 학습 기록입니다.
> Claude와의 대화 내용을 Claude가 초안으로 정리하고, 제가 검토·수정했습니다.
{: .prompt-info }

리뷰 파일을 PR로 보낸 뒤에 내용을 더 고쳤다.
그러면 PR을 다시 보내야 하나? 이 질문에 답이 계속 달라져서 처음부터 정리했다.

## 출발점 — PR이 가리키는 것은 브랜치다

브랜치는 **커밋을 쌓는 줄**이다.

```
내 포크의 main:  [리뷰 작성] → [리뷰 수정] → [그다음에 하는 것]
```

PR은 이 줄을 가리키면서 "이 줄에 있는 커밋 전부를 합쳐달라"고 하는 요청이다.
**파일을 지정하는 게 아니다.**

그래서 그 줄에 커밋이 더 쌓이면, 요청 내용도 같이 바뀐다.

## 합쳐지는 것은 "차이"뿐이다

포크는 원본을 그대로 복사한 것이라, 원본에 있는 파일은 내 쪽에도 똑같이 있다.
같은 것은 차이가 아니라서 아무 일도 일어나지 않는다.

```
원본 main:   기존 파일들
내 main:     기존 파일들 + review.md
차이:                     review.md   ← 이것만 합쳐진다
```

PR 화면의 `Files changed` 를 열면 딱 이 차이만 나온다.

## 승인 전에 고쳤을 때 — PR을 다시 안 보낸다

같은 브랜치에 푸시하면 **열려 있는 PR이 자동으로 갱신된다.**

- `Commits` 탭의 숫자가 늘어난다
- `Files changed` 는 최종 상태를 보여준다

다시 보내려고 해도 GitHub이 "이미 열려 있다"며 막는다.

## 병합된 뒤에 고쳤을 때 — 새 PR을 보낸다

병합되면 PR이 닫히고, **닫힌 PR에는 커밋이 더 붙지 않는다.**
그 뒤의 수정은 새 PR로만 간다.

이때도 브랜치를 새로 만들 필요는 없다. 리뷰를 계속 고치는 것은 목적이 같은 작업이라,
`main` 에 커밋·푸시하고 새 PR을 보내면 된다. 차이는 새로 고친 부분만 잡힌다.

## 그럼 브랜치를 새로 만들어야 할 때는 언제인가

조건은 하나다. **열려 있는 PR이 있는데, 목적이 다른 작업을 따로 보내고 싶을 때.**

예를 들어 리뷰 PR이 아직 검토 중인데, 코드에서 오타를 하나 발견해서 그것도 보내고 싶다.
`main` 하나만 쓰면 오타 수정도 같은 줄에 쌓이니까 리뷰 PR에 딸려 들어간다.

```
PR #1 = 리뷰 + 오타 수정   ← 하나로 묶여 버린다
```

### 왜 묶이면 안 되나

**승인은 PR 단위다.** 파일 하나만 골라서 승인하는 기능이 없다.

상대방이 내 리뷰를 받으려고 승인 버튼을 누르면, 그 안에 있는 코드 수정까지
자기 프로젝트에 같이 들어간다. 리뷰만 받으려고 눌렀는데 자기 앱이 바뀌는 것이다.

리뷰 파일 하나 추가하는 건 아무것도 안 바꾸니 무해하다.
하지만 남의 코드를 고친 게 섞여 있으면 그 사람 앱이 실제로 달라진다.

브랜치를 나누면 줄이 두 개가 되고, PR도 두 개가 되어 각각 따로 승인된다.

```
review-1 :  [리뷰 작성] → [리뷰 수정]     → PR #1
fix-typo :  [오타 수정]                   → PR #2
```

## 다른 사람의 저장소라면

저장소가 다르면 포크도 클론도 별개이고, `main` 도 각자 따로 있다.
A님 포크의 `main` 과 B님 포크의 `main` 은 이름만 같은 남남이라 섞일 일이 없다.

그래서 **다른 저장소에 보내는 PR은 `main` 에서 보내도 된다.**
같은 저장소에 열려 있는 PR이 있을 때만 신경 쓰면 된다.

## 한 장으로

| 상황 | 어떻게 |
|---|---|
| 승인 전에 같은 내용을 고침 | 그냥 푸시. PR 자동 갱신 |
| 병합된 뒤에 같은 내용을 고침 | 새 PR. 브랜치는 `main` 그대로 |
| 열려 있는 PR이 있는데 다른 작업을 보냄 | 브랜치를 새로 만든다 |
| 다른 저장소에 보냄 | `main` 에서 보내도 된다 |
