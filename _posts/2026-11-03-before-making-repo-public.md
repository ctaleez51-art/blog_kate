## 제출물은 공개 저장소다

세법 뉴스레터 과제는 GitHub 공개 저장소 주소로 제출했다. 저장소에 올라가는 것은 누구나 볼 수 있다. GitHub Actions 실행 로그도 공개다.

## 캡처 맨 위에 실명이 있었다

보고서의 실행 기록에는 Discord 화면 캡처가 들어가야 한다. 내가 캡처해서 `docs/discord.png`로 저장했다.

올리기 전에 이미지를 확인해 보니 **맨 위 서버 이름 줄에 실명이 들어 있었다.** 과정 수강생들이 쓰는 서버라 이름에 실명이 붙어 있었다. 서버 이름 줄을 잘라 낸 뒤 다시 확인하고 올렸다.

## 커밋마다 본 것

- 커밋에 들어가는 파일 목록
- 변경 내용에 OpenAI 키, Discord 웹훅 주소, 이메일, 실명이 없는지
- 처음부터 `.gitignore`로 올리지 않은 것: `.env`(키), 인수인계 파일, 교안 원문

마지막에 GitHub에서 직접 확인했다.

- 로컬과 GitHub의 최신 커밋이 같은지
- 인수인계 파일, `.env`, 교안 원문이 올라가지 않았는지
- 저장소가 공개 상태인지

## README가 없었다

제출 직전에 보니 README가 없었다. 교안의 제출 파일 예시(`graph.py`, `run.py`, `audience.yaml`, `requirements.txt`, `store/metrics.jsonl`, `REPORT.md`)에 README가 없어서 만들지 않았던 것이다.

README가 없으면 저장소 첫 화면에 파일 목록만 보인다. 무엇을 하는 저장소인지 알려면 REPORT.md를 직접 열어야 한다.

짧은 README.md를 만들었다.

- 무엇을 하는 에이전트인지 두세 줄(새 글은 전부 싣고 핵심만 자세히)
- 흐름 한 줄(수집 → 선별 → 요약 → 검수 → 발행)
- 실행 방법
- 파일별 역할 표
- REPORT.md 링크

자세한 설명은 REPORT.md에 있으니 README에 다시 쓰지 않고 링크로만 연결했다. 같은 내용을 두 군데 쓰면 한쪽만 고쳐지는 일이 생긴다.

## 보고서 실행 기록

REPORT.md 5절(실행 기록)은 이렇게 채웠다.

- **과제 제출용 실행**: GitHub Actions 수동 실행 로그, 실행 링크, Discord 캡처. "과제 제출용은 수동 실행, 평소에는 매일 12:00 예약 실행"이라고 밝혔다.
- **앞선 두 번의 실패**: 캡처에 같이 보이는 실패 메시지 두 개를 표로 설명했다. 원인, 대응, 그리고 글이 버려지지 않고 목록으로 발송된 것.
- **첫 실제 발송**: 오전에 로컬에서 보낸 80건 기록. 선별 근거(어떤 기준으로 무엇이 뽑혔는지)는 이 실행으로 남겼다. 제출용 실행은 새 글이 1건이라 고르는 과정이 없었기 때문이다.

## 남길 것

- 공개 저장소에 이미지를 올리기 전에 **화면 구석까지** 본다. 서버 이름, 탭 제목, 사용자 이름 같은 곳에 개인정보가 있다.
- 교안의 파일 목록은 최소 조건이다. 저장소 첫 화면에서 무엇인지 알 수 있게 README를 둔다.
- 보고서의 실행 기록은 가장 잘 나온 실행만이 아니라, 무엇을 근거로 무엇을 보여 주는지에 맞춰 고른다.
