교안 노드 여섯 묶음(LangGraph, 고객 응대 라우팅과 그라운딩, 딥리서치 오케스트레이션 1·2, 딥리서치 프로젝트, 사람이 승인하는 에이전트 프로젝트)을 한 편으로 정리한다. 앞쪽은 용어와 이론, 뒤쪽은 내가 폴더에 남긴 실습·과제 기록이다.

여섯 묶음을 관통하는 질문은 하나다. **"실행 경로(구조)를 누가, 언제 정하는가."**

| 고객 응대 라우팅 | 개발자가 분기 목록을 코드에 적을 때 + 모델이 분류만 함 |

# 1. 용어 정리

## 1-1. LangGraph 기본

| 용어 | 뜻 |
|---|---|
| 워크플로 / 에이전트 | 작업 순서를 개발자가 코드로 정하면 워크플로, LLM이 매 단계 스스로 정하면 (좁은 의미의) 에이전트 |
| 증강된 LLM | LLM + 검색 + 도구 + 메모리. 그래프의 노드 하나하나가 이 덩어리 |
| 도구(Tool) | LLM이 호출할 수 있게 등록해 둔 함수. LLM은 요청만 하고 실행은 코드가 한다 |
| State | 노드들이 함께 읽고 쓰는 공용 데이터 |
| Node | State를 받아 바뀐 부분만 딕셔너리로 돌려주는 파이썬 함수 |
| Edge | 다음에 갈 노드. `START`·`END`는 시작·종료 지점 |
| 조건부 엣지 | State를 보고 다음 목적지를 반환하는 엣지. 분기와 반복을 모두 표현 |
| 부분 업데이트 | 노드가 반환하지 않은 키는 지워지지 않고 이전 값을 유지 |
| 슈퍼스텝 | 한 스텝에서 준비된 노드를 동시에 실행하고, 끝나면 반환값을 한꺼번에 병합하는 단위 |
| 리듀서 | 같은 키에 여러 값이 올 때 합치는 규칙. 없으면 `InvalidUpdateError` |
| 팬아웃 / 팬인 | 하나에서 여러 노드로 갈라짐 / 여러 노드가 하나로 모임 |
| `Send` | 실행 중에 노드를 필요한 수만큼 복제해 동시에 실행. 워커는 자기 전용 상태만 본다 |
| `bind_tools` / `ToolNode` | 모델에 도구를 붙임(실행은 안 함) / `tool_calls` 요청을 실제로 실행 |
| ReAct | 관찰과 행동을 반복하며 푸는 구조 |
| 구조화 출력 | 응답을 지정한 스키마로 받는 방식. `Literal`이면 정해진 값 외에는 못 나온다 |
| 게이트 | 확률적인 LLM 단계 사이에 넣는 결정적(코드) 검사 |
| `recursion_limit` | 스텝 상한(기본 25). 넘으면 `GraphRecursionError`로 중간 결과가 날아간다 |
| LangSmith | 환경 변수만 설정하면 노드별 프롬프트·토큰·시간을 트레이스로 남기는 관측 도구 |

## 1-2. 고객 응대(라우팅·그라운딩)

| 용어 | 뜻 |
|---|---|
| 라우트 | 에이전트가 요청을 처리하는 경로. 개수는 회사 업무 분류(매뉴얼)를 따른다 |
| 평가셋 / 데이터 누수 | 모델보다 먼저 고정하는 시험지 / 예시로 쓴 문항이 평가에 섞이는 것 |
| 기준선(baseline) | 가장 단순한 방법(키워드 규칙 라우터)의 점수. 이후 비교의 기준 |
| 정밀도·재현율·F1·macro F1 | 예측한 것 중 맞은 비율 / 실제 중 찾은 비율 / 둘의 조화 / 클래스별 F1을 같은 비중으로 평균 |
| 혼동 행렬 | 행 = 정답, 열 = 예측. 오답이 몰린 칸이 먼저 고칠 곳 |
| 확신도·임계값·이관 | 모델이 낸 0~1 값 / 이관 기준선 / 상담원에게 넘기기 |
| 자동화율 | 이관 없이 처리한 비율. 임계값을 올리면 정확도는 오르고 자동화율은 내려가는 맞바꿈 |
| 그라운딩 | 답을 매뉴얼·조회 결과에만 근거해 만드는 것 |
| 가드레일 | 답변 속 숫자의 출처(조회 결과·매뉴얼 고정값)를 역추적해 출처 없는 숫자를 잡는 검사 |
| 엔티티 링킹 | 고객이 말한 "원피스"를 카탈로그의 상품 ID에 연결하는 일 |
| 체크포인터 / `thread_id` | 단계마다 상태를 저장하는 부품 / 대화(요청) 구분 값 |

## 1-3. 딥리서치(오케스트레이션)

| 용어 | 뜻 |
|---|---|
| 코디네이터 / 서브에이전트(리서처) | 목차를 짜고 나눠 맡기는 쪽 / 한 절씩 읽고 쓰는 쪽. 같은 모델이 프롬프트에 따라 둘 다 된다 |
| 동작하는 뼈대(Walking Skeleton) | 빈 노드를 모두 연결해 먼저 한 바퀴 돌려 보는 것 |
| 문서 카드 | 코디네이터에게 보여 주는 제목 + 앞 250자 |
| 폭 / 깊이 | 절 수 / 절당 읽기 예산. 총량 = 절 수 × 예산 |
| 컨텍스트 격리 | 원문은 서브에이전트 안에서만 읽고 위로는 원고만 올리는 설계. 격리율 = 코디네이터가 읽은 글자 ÷ 팀 전체가 읽은 글자 |
| 자기신고 / 재위임 | 리서처가 원고와 함께 `충분`·`부족`을 적어 보냄 / 부족한 절만 다시 내보냄 |
| 대리 지표 | 알고 싶은 것(글이 좋은가) 대신 세기 쉬운 것(근거율 등)을 보는 지표 |
| 신호 vs 경보 | 높낮이를 견주는 지표 / 0이어야 하는 지표(허위 인용) |
| 오귀속 | 읽은 문서를 엉뚱한 문장에 붙인 인용. 어떤 자동 지표도 못 잡는다 |
| 소거 실험(ablation) | 장치를 하나씩 끄고 같은 잣대로 다시 재는 실험 |
| 대조군 | 비교 상대. 같은 자료·모델·도구·예산을 줘야 공정 |

## 1-4. 사람이 승인하는 에이전트

| 용어 | 뜻 |
|---|---|
| HITL(Human-in-the-Loop) | 위험한 건에서만 멈추고 사람의 답을 받아 이어가는 구조 |
| `interrupt` / `resume` | 그 자리에서 멈추고 내용을 담당자에게 전달 / `Command(resume=답)`으로 멈춘 자리부터 이어감 |
| 체크포인트 | 단계가 끝날 때마다 저장되는 기록(값 + 다음에 실행할 단계 이름) |
| `InMemorySaver` / `SqliteSaver` / `PostgresSaver` | 메모리(끄면 사라짐) / 파일 / 데이터베이스(여러 서버 공유) |
| 개입률·놓침·헛멈춤 | 사람에게 온 비율 / 봤어야 하는데 자동으로 나간 건(가장 비싼 실수) / 볼 필요 없는데 온 건 |

# 2. 주요 이론

## 2-1. LangGraph — 다섯 가지 워크플로 패턴

한 번의 호출에 요구를 여러 개 담으면 일부를 빠뜨리고 어디서 틀렸는지도 모른다. 그래서 작업을 단계로 나누고, 순서·갈림길·도구를 코드로 정한다. Anthropic의 조언은 가장 단순한 워크플로로 시작하고, 자율성이 꼭 필요하다는 증거가 있을 때만 에이전트로 가는 것이다.

| 패턴 | 맞는 문제 | 그래프 핵심 | 대가 |
|---|---|---|---|
| 프롬프트 체이닝 | 단계에 순서가 있고 중간 점검이 필요 | 순차 노드 + 코드 게이트 | 단계 수만큼 지연 |
| 라우팅 | 입력 유형별로 처리가 완전히 다름 | 분류 노드 + 점선 조건부 엣지 | 분류 오류가 전체를 망침 |
| 병렬화 | 독립 하위 작업, 개수를 미리 앎 | 실선 팬아웃 + 리듀서 | 시간은 줄고 토큰 비용은 그대로 |
| 오케스트레이터-워커 | 하위 작업 개수·내용이 실행 중 정해짐 | 오케스트레이터 + `Send` | 계획이 나쁘면 전부 나쁨, 비용 예측 불가 |
| 평가자-최적화자 | 기준이 분명하고 고칠수록 나아짐 | 생성↔평가 순환 엣지 | 라운드마다 비용, 상한 필수 |

핵심만 추리면 이렇다.

- **노드가 반환하지 않은 키는 유지된다.** 같은 스텝에 같은 키를 두 노드가 쓰면 에러이고, 리듀서로 합치는 규칙을 정해야 한다.
- **도구를 정의할 때는 독스트링이 곧 사양서다.** LLM은 파이썬 코드가 아니라 스키마만 본다. 도구 호출이 엉뚱하면 프롬프트보다 독스트링을 먼저 의심한다.
- **`bind_tools`는 요청만 만든다.** 실행은 `ToolNode` 같은 코드가 한다.
- **게이트는 누락만 잡는다.** 용어가 들어 있는지는 보지만 맞게 설명했는지는 못 본다.
- **라벨이 배타적이지 않으면 라우팅이 어렵다.** 코드와 설명이 같이 있는 노트는 프롬프트를 고쳐도 정확도가 안 올랐다. 겸할 수 있으면 병렬화, 배타적이면 라우팅.
- **워커에게 근거를 주지 않으면 환각이 난다.** 제목만 받은 워커가 LangGraph 리듀서 대신 JavaScript Redux를 설명했다. 환각은 프롬프트보다 근거를 줄 때 가장 확실히 줄어든다.
- **평가 루프는 규칙을 채우는 쪽으로만 바꾼다.** "원래 주제를 유지하는가"가 기준에 없으면 주제가 바뀐다. 코드로 되는 것은 코드로(게이트), 상한은 `recursion_limit`만 믿지 말고 State에 횟수를 세어 정상 종료 경로를 둔다.
- **워크플로로 안 된다는 증거가 나오기 전에는 에이전트로 가지 않는다.** 필요한 단계 조합을 개발자가 미리 열거할 수 없을 때가 기준이다.

## 2-2. 고객 응대 에이전트 — 라우팅과 그라운딩

문의 분류 → 정보 조회 → 정책 근거 답변 → 숫자 오류 검사를 하나의 파이프라인으로 만든다. 가상 쇼핑몰 '모두몰'의 문의 193건, 라우트 5종(`ORDER_PLACE`·`PRODUCT_INFO`·`SHIPPING`·`RETURN_REFUND`·`OTHER`)이 대상이다.

1. **라우트는 개발자가 정하지 않고 매뉴얼에서 가져온다.** 매뉴얼의 4개 유형에, 응대 범위 밖(오프라인 매장 등)을 다섯 번째 `OTHER`로 둔다. 구분하지 않으면 없는 매장 주소를 지어내는 오답이 생긴다.
2. **평가셋을 먼저 고정한다.** 예시용 40건과 평가용 120건을 분리하고 겹치는지 점검한다. 프롬프트부터 쓰면 수정 후 정말 좋아졌는지 알 수 없다.
3. **키워드는 표현을 찾고, 라우팅은 의도를 판단한다.** "낱개로도 구매 가능한가요?"는 '구매 가능' 때문에 `ORDER_PLACE`로 가지만 정답은 상품 정보다. 기준은 고객이 쓴 단어가 아니라 원하는 결과다. 규칙 순서도 회사 정책(진행 중 반품 우선)으로 정해야 한다.
4. **정확도만 보면 안 된다.** 소수 클래스를 못 맞혀도 높게 나온다. 혼동 행렬의 대각선 밖 숫자가 어디를 고칠지 알려 주고, 오분류 문장을 직접 읽으면 왜 틀렸는지 알 수 있다.
5. **LLM 라우터는 `classify` 함수 하나만 갈아 끼운다.** 그래야 점수 차이의 원인이 분명하다. 출력은 `Literal`로 제한한 스키마 + 확신도 + 근거 한 문장.
6. **확신도는 믿으면 안 된다.** 경계가 모호한 문의에도 높은 확신도가 나온다. 임계값 0.5 미만이면 이관하되, 평가셋으로 실제 신뢰성을 검증한다. 자신 있게 틀린 건은 임계값을 올려도 안 걸러진다.
7. **세 가지 안전장치**: ① 라우트에 필요한 매뉴얼 장만 넣기 ② `[어드민 조회]` 표시로 조회 함수 만들기(화면 하나 = 함수 하나) ③ 가드레일.
8. **고정값은 안내하고, 건마다 달라지는 값은 조회하거나 되묻는다.** 기준액을 40,000원으로 고정하면 의류는 우연히 맞고 신발은 틀리고 화장품엔 없는 혜택을 안내한다. 계산(부족액)은 모델이 아니라 코드가 한다. 조회 결과의 `null`은 "값 없음"이 아니라 "아직 결정되지 않음"이다.
9. **규칙 목록보다 번호 붙은 절차가 낫다.** "상품명을 말하면 먼저 검색한다"를 규칙에 넣었을 땐 일관되지 않았고, 단계별 절차로 바꾸자 세 가지 표현 모두 검색 → 조회 → 답변 순서로 처리됐다.
10. **채점은 문장이 아니라 조건으로 한다.** `action`(행동), `tools`(과정도 채점), `must`(포함할 사실), `forbid`(하지 말아야 할 것), `must_ask`. 채점기를 만든 뒤 채점기 자체를 모범 답안으로 먼저 검증한다.
11. **정답셋으로는 정확성을, 실제 문의로는 병목을 본다.** 실제 문의 40건은 대부분 되묻기로 끝났다. 병목은 식별자 없음, 엔티티 링킹 부족, 확신도 미달 이관이었다.

## 2-3. 딥리서치 에이전트 — 오케스트레이션 1일차

문서 34건(447,487자, 약 22만 토큰)은 `gpt-4o-mini`의 컨텍스트(12.8만 토큰)에 안 들어간다. 그래서 코디네이터가 목차를 짜고 서브에이전트가 절마다 필요한 문서만 읽는다. 노드는 ① 기획 ② 배치 ③ 조사 ④ 점검 ⑤ 종합 ⑥ 평가 여섯 개다.

- **라우팅과의 차이는 구조가 굳는 시점이다.** 코드 작성 시 / 질문 도착 후 / 자료를 읽은 뒤. 늦을수록 유연하지만 비용과 편차가 커진다(질문당 LLM 호출 한두 번 vs 29번 안팎). 기준은 "분기를 코드에서 미리 정할 수 있는가"와 "자료를 읽어야 다음에 읽을 것을 정할 수 있는가".
- **쓰지 말아야 할 때**: 문서 한 건이면 답이 나오는 질문, 모든 에이전트가 같은 맥락을 공유해야 하는 작업(코딩). Anthropic 사례에서 멀티 에이전트는 내부 평가 90.2% 높았지만 토큰을 약 15배 썼다.
- **① 기획 — 문서 카드(제목 + 앞 250자)를 보여 준다.** 제목만 주면 을사조약 저항 질문에 《임오군란》(1882)이 배정됐다. 카드는 코퍼스의 1.9%만 추가하면서 배정을 바꿨다. 배정과 구역 설정을 켜자 중복률이 41.5% → 19.6%로 내려갔다. 목차는 내용 단위로 나눠야 하고, 형식 단위(개요·연표·인물)로 나누면 모두 같은 문서를 읽는다. 배정은 출발점일 뿐이라 리서처가 다음 문서를 직접 고를 수 있어야 한다.
- **② 배치 — 폭과 깊이는 한 덩어리다.** 총 읽기량 = 절 수 × 절당 예산. 같은 총량이면 넓게 나누는 편이 유리하다는 예측 ①, 더 읽어도 근거가 촘촘해진다는 보장은 없다는 예측 ②를 먼저 적고 2일차에 검증한다. 병렬 실행 중에는 서로의 진행 상황을 볼 수 없어서, 코디네이터가 아는 시작 문서로 "피하기" 목록을 만들어 준다.
- **③ 조사 — 요약이 아니라 인용이 붙은 절 원고를 돌려받는다.** 원문을 읽은 쪽이 직접 써야 인용이 정확하고, 코디네이터에는 원고만 올라가 컨텍스트가 격리된다. 격리는 되돌릴 수 없어서 "관련 없으면 관련 없음이라고만 답하라"는 탈출구를 둔다. 노드 안 루프에는 반드시 예산 상한을 둔다. 관련 없는 문서만 읽고도 원고가 나오면 모델이 상식으로 채운 것이고, 인용 0곳이 그 신호다.

## 2-4. 딥리서치 에이전트 — 오케스트레이션 2일차

- **④ 점검 — 자기신고.** 코디네이터가 원고를 다 읽으면 격리가 깨지므로, 원고를 쓴 리서처가 `충분`/`부족`과 사유를 적어 보낸다. 점검 노드는 LLM 호출 없이 신고만 모아 부족한 절만 다시 보낸다. 모델은 자기 일을 후하게 평가하고, "6~12문장을 못 채웠다"처럼 형식을 부족 사유로 쓰기도 한다. 멈춤 조건은 둘(빈 칸 없음, 라운드 소진)이고 멈춘 이유를 State에 남긴다.
- **⑤ 종합 — 본문은 다시 쓰지 않는다.** 편집자는 절 제목과 첫 90자만 보고 머리말·맺음말만 쓴다. 다시 쓰면 격리가 깨지고, 원문을 본 적 없는 모델이 인용을 옮기다 빠뜨린다. 대가로 절마다 문체가 다르고 중복·모순은 남는다.
- **⑥ 평가 — 정답표도 판정 모델도 쓰지 않는다.** 근거 비율, 허위 인용(경보, 0이어야 함), 읽고 안 쓴 문서, 인용 편중, 중복률. 지표마다 보는 장치가 정해져 있어서 장치를 껐을 때 "나빠졌다"가 아니라 "편중이 먼저 뛰었다"고 말할 수 있다. 근거 비율은 문장 나누기 때문에 실제보다 낮게 나온다(교안 기록 67.4%가 보정하면 85.4%). 지표로 걸러 내고, 남은 것은 사람이 읽고 고른다.
- **단일 에이전트와 공정하게 비교한다.** 대조군이 후보 밖 제목을 답하면 멈추게 짜면 12건 중 서너 건만 읽고 끝난다. 약한 상대를 만들어 놓고 이기면 실험이 아니다. 같은 자료·모델·도구·예산을 주고 예산을 다 쓰는지 확인한다.
- **소거 실험 결과(교안 기록).** 배정·구역은 질문이 달라도 일관되게 효과가 있었다(끄면 중복·편중이 두 배, 호출도 증가). 역할은 질문이 역할을 요구할 때만(인물 중심 질문) 효과가 났다. 재위임은 이 평가에서 효과를 못 봤는데, 두 번째 원고가 첫 원고를 무조건 덮어써서 인용 없는 원고가 멀쩡한 원고를 지웠기 때문이다. 한 번 돌린 결과로 방향을 단정하지 않고, 차이가 작으면 "효과 없음" 대신 "이 표본으로는 확인하지 못했다"고 쓴다.
- **남은 한계 넷**: 질문 크기를 판단하는 라우팅이 그래프 앞에 없다(한 건짜리 질문에도 리서처 넷이 뜬다) / 재위임이 첫 원고를 덮어씀 / 절 사이 중복·모순을 고치는 노드 없음 / 오귀속은 모든 지표를 통과한다.

## 2-5. 딥리서치 프로젝트

배운 것은 역사가 아니라 분업이다. 주제는 자유지만 조건이 있다: 자료 30건 이상, 총 글자 수가 컨텍스트 윈도우를 넘을 것, 자료끼리 서로를 가리킬 것, 산출물이 장문일 것. 필수 5단계는 ① 자료와 질문 세트(8건 이상, 한 건으로 답이 나오는 질문도 일부러 포함, 정답표 없음) ② 코디네이터·서브에이전트(배정을 코드가 검사, 격리를 숫자로 증명, 재위임 상한) ③ 정답표 없는 지표 ④ 결과물 직접 비교(기본·장치 끈 것·단일 대조군) ⑤ 웹 데모. 직접 해야 할 일은 세 가지다: 무엇을 절로 나눌지, 대조군이 공정한지, 에이전트 결과를 의심하는 일.

## 2-6. 사람이 승인하는 에이전트 (HITL)

- **정확도를 올려도 남는 건이 있다.** 정확도 95%에 하루 200건이면 매일 10건, 99%여도 2건이 확인 없이 나간다. 판단을 정확하게 만드는 노력과 별개로 결과가 나가기 전에 막을 자리가 필요하다.
- **세 선택지**: 전부 사람이 확인(일이 안 줄어듦) / 전부 자동(사고를 감수) / 위험한 건에서만 멈춤(HITL).
- **자리는 결과가 바깥으로 나가는 단계 바로 앞이다.** 만드는 일과 보내는 일을 다른 단계로 나누면 그 사이가 자리가 된다.
- **멈추고 이어가는 방식**: `interrupt`가 그 자리에서 멈추고, 상태는 체크포인터에 `thread_id`별로 저장된다. `Command(resume=답)`으로 이어가면 처음부터가 아니라 멈춘 지점부터 실행된다. 체크포인터가 없으면 `interrupt`를 쓸 수 없다.
- **함정: 멈춘 단계는 처음부터 다시 실행된다.** 체크포인트에는 단계 이름만 있고 몇 번째 줄인지는 없다. 멈추기 전에 문자를 보내 두면 고객이 두 번 받는다. 원칙은 "사람에게 묻는 단계 안에서, 묻기 전에 바깥으로 나가는 동작을 두지 말 것".
- **멈춤 기준은 계산 가능한 형태로 쓰고, 개입률·놓침·헛멈춤으로 검증한다.** "금액이 크면"이 아니라 "30,000원을 넘으면". 환불 5건 예제에서 금액 기준 하나는 R3(31만 원)만 잡고 R5(단순 변심, 9천 원)는 놓쳤다. 다른 종류의 기준(표현)을 하나 더하면 놓침·헛멈춤이 모두 0이 됐지만 5건짜리라서다. 헛멈춤이 많으면 담당자가 내용을 안 보고 승인만 누른다.
- **승인 화면은 10초 안에 판단할 수 있어야 한다.** 요청 원문, 핵심 정보, AI의 판정과 근거 규정, 왜 멈췄는지, 통과시키면 무슨 일이 일어나는지. 마지막 줄이 승인 버튼의 무게를 바꾼다. 응답은 승인·수정 후 승인·반려(사유 포함)·다시 판정 네 가지다.
- **대기는 초 단위가 아니다.** 대기 건은 파일·DB 체크포인터에 두고, 3일 넘게 처리되지 않으면 어떻게 할지 운영 규칙까지 정한다.
- **프로젝트 필수**: 결과를 내보내기 직전에 멈추고 이어가는 파이프라인 / 계산 가능한 승인 기준 2개 이상과 이유 / 대기 목록과 승인·반려가 되는 웹 데모. 실습에서 다룬 환불 승인은 주제에서 제외.

## 3-2. 고객 응대 에이전트 (`class\cs-agent`, VS Code 노트북)

## 3-3. 딥리서치 에이전트 (`class\deepresearch-agent`, 1·2일차)

질문 "1894년에 일어난 주요 사건들은 무엇이고 각각의 원인은 무엇인가?"로 하루에 1·2일차를 모두 실습했다. 노트북은 1일차 `deepresearch.ipynb`, 2일차는 1일차 셀 뒤에 2일차 셀을 이어 붙인 `deepresearch_1-2일차.ipynb`. 모델을 부르는 셀에는 결과를 `결과/*.pkl`로 저장하고 이미 있으면 다시 부르지 않는 껍데기를 씌웠다. 그래서 커널을 다시 켜도 비용이 다시 들지 않는다.

**1일차에서 확인한 것**

- 설치 셀에서 `ERROR: Invalid requirement: '#'`가 났다. 교안은 리눅스 기준이라 `!` 줄 끝의 `#` 뒤를 주석으로 보지만, Windows에서는 pip가 `#`을 패키지 이름으로 받는다. 주석을 윗줄로 옮겨 해결했다.
- ① 기획: 목차 4절. 《을미사변》은 1895년 사건이라 1894년 질문에서 벗어났고, 사건 절에 인물 담당이 붙는 등 절 성격이 아니라 명단 순서대로 역할이 붙은 것처럼 보였다. 코드는 형식만 검사하지 내용이 질문에 맞는지는 판단하지 못한다.
- ③ 조사: 네 절 모두 3건씩 읽었고 허위 인용은 없었다. 그런데 임오군란 절은 인용 0곳인데 자기평가는 "충분"이었다. 《갑신정변》은 세 절이 각각 읽었다. 1바퀴 `피하기` 목록에는 시작 문서만 들어가서 막히지 않는다.
- 1-6, 1-7, 1-9 셀은 모두 `run()`으로 그래프를 처음부터 다시 돌려서, 셀마다 목차가 다르게 나왔다. 앞 셀의 로그와 이 셀의 결과는 서로 다른 실행이다.

**2일차에서 확인한 것**

- ④ 점검: «청일 전쟁»만 "운요호 사건에 대한 내용이 부족함"으로 신고해 재위임됐고, 루프가 처음 돌았다. 2라운드에서 문서 3건 → 6건, 465자 → 570자, **인용 7곳 → 0곳**. 1라운드에 이미 《운요호 사건》을 읽었으니 부족한 것은 자료가 아니라 원고였는데, 재위임은 "안 본 문서를 찾아라"라서 엉뚱한 문서를 읽게 했다.
- ⑤ 종합: 완성된 보고서의 4절 «을미사변»에는 인용이 하나도 없고 1895년 사건이다. 머리말은 을미사변을 1894년 사건으로 소개했다(편집자가 첫 90자만 봐서 못 잡음).
- ⑥ 평가: 문장 43 · 근거 69.8% · 허위 0 · 읽고 안 쓴 문서 6건 · 편중 17.6% · 중복 22.2% · LLM 40회.

| 비교 | 결과 |
|---|---|
| 폭과 깊이 | 4절×2건이 근거 62.2% · 편중 22.2%, 4절×3건은 근거 32.0%로 오히려 낮아짐. 읽기·분량·호출만 늘었다 (예측 ①·② 모두 맞음) |
| 팀 vs 단일 | 호출은 비슷(26회 vs 25회)한데 팀 보고서가 두 배 이상 길고 인용은 34곳 vs 4곳. 단일은 12건을 읽고 8건을 한 번도 안 썼다 |
| 세 질문 | 운요호 사건 한 건짜리 질문을 네 절로 쪼개니 읽고 안 쓴 문서 7건. 쪼갤 필요 없는 질문에는 라우팅이 필요하다 |
| 소거 | 배정·구역을 끄면 중복 16.7% → 33.3%, 편중 19.4% → 34.6%, 호출 26 → 30. 가장 분명한 결과 |

- 재위임 끄기는 **판단하지 못했다.** 기준 실행에서 재위임이 한 번도 일어나지 않아 호출이 똑같이 26회였고, 두 줄의 차이는 실행마다의 흔들림이다. 기준 설정만도 62.8%와 66.7%로 움직였다. "효과 없음"이라고 쓰려면 ① 장치가 실제로 작동했는지 ② 기준을 여러 번 돌려 흔들림 크기를 쟀는지 ③ 질문을 바꿔서도 확인했는지를 먼저 봐야 한다.
- `결과자료.json`의 문장을 `corpus.json` 원문과 직접 대조했다. "…이는 청일 전쟁의 배경이 되었다 «운요호 사건»"은 원문에 '청일'이라는 말이 한 번도 없다. 사실은 그 문서에서 왔지만 청일 전쟁과의 연결은 리서처의 해석이다. 이런 문장도 근거 비율에서는 근거 있는 문장이고 허위 인용도 0이다. 가장 좋은 기록 안에도 오귀속이 있었다.

**3D 시뮬레이터.** 같은 파이프라인을 3D 화면으로 보는 시뮬레이터(`simulator`)를 만들었다. 모델 호출을 감싸는 래퍼로 노드 시작·끝 이벤트를 뽑아 `runs/*.json`에 저장하고, 도서관 마을(책장 34개 = 문서)로 재생한다. 겪은 것 세 가지가 남는다.

- Windows에서 기록 파일 덮어쓰기가 거부돼(`PermissionError: [WinError 5]`) 첫 실행이 23.7초에 끊겼다. 다시 시도하고 그래도 안 되면 실행은 계속하도록 고쳤다.
- 고쳐 저장했다는 파일이 실제로는 예전 파일이어서 내가 다시 켜 보고 알았다. 파일을 바꾼 뒤에는 PC 쪽 내용이 바뀌었는지 확인한다.
- 위쪽 **실행**은 파이프라인을 새로 돌리는 것(비용), 아래쪽 **재생**은 기록을 다시 보는 것(비용 없음)이다.

# 4. 과제 기록

## 4-1. 인적공제 상담 라우팅 에이전트 (`tax-routing-agent`, 11/8)

고객 응대 교안 10장의 과제다. RAG 챗봇 과제에서 쓴 인적공제 자료로, 질문을 카테고리(`FAMILY`·`INCOME`·`EXTRA`·`CREDIT`·`OTHER`)로 나눈 뒤 그 카테고리의 근거만으로 답한다. 구조는 실습과 같다: 판정 → 카테고리별 근거 조립 → 근거만으로 답변 → 검증, 그리고 `OTHER`·확신도 0.5 미만·근거에 답 없음·검증 위반이면 상담원에게 넘긴다.

- 평가셋은 22건(RAG 과제 고정 질문 11개 포함)이고 예시용 5건은 따로 뒀다.
- **채점기부터 채점했다.** 모범 답안 18/18 통과, 일부러 틀린 답 18/18 탈락을 확인한 뒤에 모델 결과를 쟀다.
- 판정은 `gpt-5.6-luna`, 답변과 채점은 `gpt-5.6-terra`를 썼다(원래는 로컬 `qwen3.5:2b`였지만 제출 시간이 빠듯해 바꿨다).

| 지표 | 기준 실행 | 개선 1 |
|---|---|---|
| 분류 정확도 / macro F1 | 1.000 / 1.000 | 1.000 / 1.000 |
| 도구 호출 적절성 | 0.955 | 1.000 |
| 답변 적절성 | 0.909 | 0.955 |

- 개선은 **답변 규칙 한 줄만 바꿔서** 다시 쟀다. 하나만 바꿔야 원인을 말할 수 있다. 개선 뒤에도 M02 한 건은 그대로 남아, 제출 뒤 보완점으로 적어 뒀다.
- 데모는 Streamlit으로 만들어 판정·부른 도구·답변·검증 결과·근거를 위에서 아래로 보여 주고 화면을 두 장 캡처했다.

## 4-2. 종합소득세 딥리서처 (`tax-deep-researcher`, 11/6~)

딥리서치 프로젝트 과제다. 한국 근대사 대신 직접 만들고 있는 종합소득세 신고 앱에서 AI가 맡을 상담의 원형으로 주제를 잡았다.

**코퍼스.** 소득세법·시행령·시행규칙·기본통칙·집행기준 1,657건, 1,044,872자(`gpt-4o-mini` 컨텍스트의 4.08배), 링크 7,340개. 법 조문끼리 "법 제27조", "영 제55조"처럼 서로를 가리키는 점이 링크 탐색에 맞다. 링크가 0개인 문서가 39건이라 배정으로만 닿는다.

**분업 설계.** 목차는 내용 단위로 나누고 배정은 코드가 검사한다. 4절 × 4건(조문이 위키 문서보다 짧아서 교안의 3건에서 한 건 늘림). 두 번째 원고는 덮어쓰지 않고 읽은 문서를 인용한 수가 많은 쪽을 남긴다(교안 소거 실험에서 겪은 덮어쓰기 문제 때문). 역할은 소득구분·필요경비·공제감면·신고절차·불이익·해석 담당으로 새로 짰다.

**결과 분석에서 배운 것.**

- 첫 실행의 근거율이 평균 18.4%, 인용 0곳 경보가 14개였다. 기록을 열어 보니 모델이 아니라 코드 버그 두 개였다. ① 카드가 `소득세법 제70조(종합소득과세표준 확정신고)` 꼴이라 코디네이터가 제목까지 붙여 답했고 코드는 이를 없는 문서로 보고 법률 목록 맨 앞으로 바꿨다. ② 자료 머리가 `[문서명]` 꼴이라 리서처가 `«»` 대신 `[ ]`로 인용했고 코드는 `«»`만 셌다. 둘을 고치자 32.6%가 됐다. ①만 고친 실행은 오히려 5.4%였다. **지표가 나쁠 때 "모델이 못 한다"고 결론 내기 전에 기록부터 열어야 한다.** 모델에게 보여 주는 형식과 코드가 기대하는 형식은 한 곳에서 정해야 한다.
- 팀(기본)이 단일 대조군보다 낫다. 같은 16건을 읽고도 단일의 보고서는 절반 길이였고 인용의 75~100%가 한 문서에 몰렸다. 근거율 하나로만 순위를 매기면 단일이 이기는 것처럼 보이는 경우도 있어서 편중과 길이를 같이 봐야 한다.
- 재위임은 근거율을 올리지 못했다. 40절 중 9절이 "부족"을 신고했고 2바퀴 원고 9개가 모두 다시 "부족"을 신고했다. 원하는 근거가 코퍼스 밖(국세기본법)이거나 그림으로 빠진 계산식이라 다시 보내도 못 찾는다. 재위임 전에 "이 부족이 코퍼스 안에서 채워질 수 있는가"를 판단해야 한다.
- 같은 설정 안에서도 근거율이 최대 30%p 움직였다. 2회 반복으로는 장치를 끈 효과를 가릴 수 없어서, 반복을 늘려 편차보다 큰 차이만 결론으로 삼기로 했다.
- 원문과 직접 대조한 것: 허위 인용(코퍼스에 없는 국세기본법 제48조), 기부금 제34조 ⑤항의 괄호 단서 누락(인용은 제자리인데 핵심 단서를 놓침), 원본의 그림 계산식이 빈 줄이 된 것. 모두 지표로는 안 잡히고 원문을 열어야 보였다.
- 한 건이면 되는 질문(Q1 확정신고 기한)에 절 4개·LLM 43회가 들어갔다. 질문 크기를 먼저 판단하는 라우팅이 필요하다.

**11/10 수정 중.** 원인 여섯 가지(자료 없이 절을 쓰게 함, 시작 조문 배정 오류, 후보를 가나다순으로 고름, 법률→시행령 링크 누락, 작성자가 요약만 봄, 문장·원문 대조 없음)를 고치고 Q3·Q5·Q10을 다시 돌렸다. 3차 실행에서 근거율 76.9 · 82.6 · 75.0%, "관련 없음" 비율 53% → 10%가 됐다. 다만 이 수정은 아직 커밋하지 않았고 미완성이다. Q10의 괄호 단서는 여전히 빠졌고, 엄격한 검증 때문에 보고서가 조문을 그대로 옮긴 나열에 가까워진 문제가 남았다. 어느 수정이 효과를 냈는지는 나누어 재지 않았다.

## 4-3. 사람이 승인하는 에이전트 (`hitl-agent`, 진행 중)

- **실습**: 노트북에서 섹션 2(멈췄다가 담당자 답변으로 이어가기, 체크포인터에 저장된 내용 보기)와 섹션 3(여섯 가지 멈춤 기준 비교)을 실행했다. 이 실습은 시각화하기로 하고 체크포인트·기준 비교를 `결과\기록.json`에 14건 쌓았다. 그리기는 아직 하지 않았다.
- **주제**: 인적공제 상담 답변을 고객에게 보내기 전에 사람이 승인한다. 위 라우팅 과제의 파이프라인에 승인 단계를 붙인다. 모델은 확신도가 전부 0.98 이상인 OpenAI 모델로는 기준을 검증하기 어려워서, 틀리는 건이 나올 작은 로컬 모델(`qwen3.5:2b`)로 바꾸기로 했다.
- **기준 후보 검토**: 라우팅 과제의 평가 기록 36건으로 기준별 개입·놓침·헛멈춤을 셌다(코드는 만들지 않고 데이터만 봄).

| 기준 | 멈춤 | 놓침 | 헛멈춤 |
|---|---|---|---|
| 확신도 0.7 미만 | 0/36 | 3 | 0 |
| 답변에 금액 포함 | 18/36 | 1 | 16 |
| 카테고리 2개에 걸친 질문 | 5/36 | 1 | 3 |
| "장애" 포함 | 4/36 | 0 | 1 |
| 카테고리 2개 또는 "장애" | 7/36 | 0 | 4 |

- 이 표가 말하는 것: 확신도 기준은 모델이 확신을 과하게 내서 하나도 못 잡았고, 금액 기준은 절반을 멈추게 해서 사람이 다 보게 된다. **기준 하나로는 안 되고 종류가 다른 기준을 더해야 한다**는 교안의 결론과 같다.
- 아직 정하지 못한 것: 승인 기준 2개 이상, 진행 방식. 과제 조건(웹 데모, README, REPORT)은 이 정리 이후에 만든다.

# 5. 정리

- 구조를 정하는 시점이 늦어질수록 유연하지만 비용과 편차가 커진다. **코드에서 정할 수 있으면 워크플로·라우팅, 자료를 읽어야 정해지면 오케스트레이터, 되돌릴 수 없는 일 앞에서는 사람.**
- 점수 하나로 장치의 효과를 단정하지 않는다. 장치가 실제로 작동했는지, 흔들림이 얼마인지, 질문을 바꿔도 같은지를 먼저 본다.
- 지표가 나쁠 때는 기록을 열어 코드 버그(형식 불일치)인지 모델 문제인지부터 가른다.
- 자동 지표는 명백한 실패를 거르는 데만 쓰고, 오귀속처럼 지표를 통과하는 문제는 사람이 원문과 대조한다.
- 모델이 잘 못하는 것(계산, 출처 확인)은 코드로 빼고, 하지 말아야 할 것은 `forbid`나 가드레일로 검사한다.

## 앱과 연결 (diy-wai)

- 신고 앱의 상담 기능은 딥리서치 구조를 그대로 쓰기보다, 질문 크기에 따라 단일 조회와 딥리서치를 나누는 라우팅이 앞에 필요하다.
- 답마다 인용한 조문 원문을 열어 볼 수 있어야 한다. 오귀속은 사람이 원문과 대조해야 잡힌다.
- 고객에게 나가는 답변처럼 되돌릴 수 없는 출력 앞에는 승인 단계가 필요하고, 그 기준은 확신도 하나가 아니라 종류가 다른 기준을 함께 둬야 한다.
